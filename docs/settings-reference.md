# Application Settings Reference

DocMergeForge has application-level desktop settings represented by `AppSettings`. These preferences are distinct from per-project `MergeSettings`: application settings control desktop defaults/convenience behavior, while project settings describe a particular publication.

## Current defaults

```json
{
  "theme": "system",
  "default_output_folder": "",
  "temporary_directory": "",
  "worker_count": 2,
  "logging_level": "INFO",
  "checksum_generation": true,
  "automatic_validation": true,
  "pdf_optimization": "preserve",
  "docx_fidelity_mode": "portable",
  "crash_recovery": true,
  "merge_profile": "Exact Preservation",
  "filename_template": "{series}_Complete_{part_count}_Part_Master_Edition",
  "libreoffice_integration": true,
  "word_high_fidelity": false,
  "recent_project_history": true,
  "reduced_motion": false,
  "text_scale_percent": 100,
  "first_run_completed": false
}
```

## `theme`

Default:

```text
system
```

Controls the desktop appearance preference. The application should follow supported system/light/dark behavior without using color as the only carrier of important validation state.

## `default_output_folder`

Default: empty string.

Optional default destination shown/used by desktop workflows. A project still stores its own output folder, and production preflight always needs to verify that actual project destination is writable and has sufficient space.

Do not assume a default output path is valid after moving a project to another machine.

## `temporary_directory`

Default: empty string.

Reserved/configurable location for temporary behavior where supported by the application. The final project publication transaction itself intentionally stages inside the selected output filesystem so final rename/replacement behavior can be safe and recovery-aware.

A custom temp preference should never be used to bypass the transaction's output-folder safety requirements.

## `worker_count`

Default:

```text
2
```

Desktop/application concurrency preference. The settings UI and loader constrain this value to `1–64`. Actual document engine work can include inherently sequential stages because source order, Word composition, and final transaction promotion must remain deterministic.

Increasing worker count is not a guarantee of faster large merges and should be stress-tested before changing performance claims.

## `logging_level`

Default:

```text
INFO
```

Controls diagnostic log threshold where connected to logging configuration.

Supported persisted values are:

```text
DEBUG
INFO
WARNING
ERROR
```

An invalid stored value is reset to `INFO` during settings loading.

Higher verbosity can expose more local paths/technical details, so review diagnostics before sharing.

## `checksum_generation`

Default:

```text
true
```

Controls whether checksum evidence is generated by project publication where the project/settings flow uses this preference.

Per-project `MergeSettings.checksum_generation` is the authoritative setting stored with a specific project.

## `automatic_validation`

Default:

```text
true
```

Controls the user's default expectation that validation is part of publication. Per-project configuration also contains `automatic_validation`.

Disabling a preference should not be used to bypass hard safety checks that the application service requires before a valid project publication.

## `pdf_optimization`

Default:

```text
preserve
```

Preferred PDF optimization mode for project creation/settings UI. Supported persisted values are `preserve`, `balanced`, and `archive`; an unknown stored value falls back to `preserve`.

- `preserve` — avoid the extra content-stream compression pass;
- `balanced` — compress output page content streams;
- `archive` — also compress output page content streams under the current engine.

Always test file size/fidelity on representative publications.

## `docx_fidelity_mode`

Default:

```text
portable
```

Portable OOXML is the current production-supported mode. Supported persisted values are `portable`, `libreoffice`, and `word`; an unknown stored value falls back to `portable`.

The UI may expose capability choices, but the DOCX engine calls a production-readiness gate. An external mode cannot become production-ready merely through this setting or because Word/LibreOffice is installed.

## `crash_recovery`

Default:

```text
true
```

Controls desktop recovery/checkpoint convenience behavior.

This is conceptually separate from the output transaction journal. Even if a UI recovery preference changes, an interrupted `.docmergeforge-staging-*` publication journal must be treated as filesystem recovery evidence and resolved safely.

## `merge_profile`

Default:

```text
Exact Preservation
```

Preferred merge profile name for new/configured work. Supported stored profile names are the same values exposed by the desktop settings dialog; an unknown stored profile name falls back to `Exact Preservation`.

A project persists its own `settings.profile_name`, which is recorded in publication evidence/manifests.

## `filename_template`

Application default:

```text
{series}_Complete_{part_count}_Part_Master_Edition
```

This is a desktop/default naming preference. The `MergeSettings` dataclass currently has its own default filename template (`{series}_Master`) for directly constructed generic projects unless overridden.

This distinction matters when comparing a project created by different surfaces/versions. Always inspect `expected_outputs` during dry-run rather than inferring the filename from an application preference alone.

## `libreoffice_integration`

Default:

```text
true
```

Indicates whether LibreOffice integration/capability may be considered by the desktop settings layer.

It does **not** make the LibreOffice high-fidelity adapter production-ready. The current project documentation explicitly keeps that adapter behind an unfinished release gate.

## `word_high_fidelity`

Default:

```text
false
```

User preference related to Microsoft Word high-fidelity behavior. The current Word automation adapter is not accepted as production-ready, so turning a preference on must not bypass the DOCX fidelity safety gate.

## `recent_project_history`

Default:

```text
true
```

Enables recent-project convenience behavior in the desktop application.

Recent entries can reveal project names/local paths on a shared machine. Disable/clear them according to local privacy policy when necessary.

Malformed recent-history JSON and incomplete/non-string history entries are treated as invalid convenience metadata and skipped rather than preventing the desktop from opening. This tolerance does **not** apply to an explicitly opened merge-project file, which remains strict because inventing missing publication configuration would be unsafe.

## `reduced_motion`

Default:

```text
false
```

Accessibility preference intended to reduce nonessential motion. Essential progress/state information must remain understandable even when motion is reduced.

## `text_scale_percent`

Default:

```text
100
```

Desktop text-size preference. The settings UI and loader constrain the value to `80–200` percent. Human accessibility acceptance should test increased values together with OS display scaling and long path/project strings.

## `first_run_completed`

Default:

```text
false
```

Tracks whether first-run onboarding has been completed. Once onboarding is finished, the value can be persisted so normal launches do not repeat the first-run experience.

This flag is convenience state, not evidence that a user has accepted a release or read every safety notice.

## Settings persistence

`AppSettings.save()` uses the shared atomic text writer. It creates a **unique sibling temporary file**, writes UTF-8 JSON, flushes and `fsync`s the temporary file, and then promotes it with `os.replace(...)`.

If writing or replacement fails, the temporary file is removed and the previously published settings file is left intact. The application does not rely on one predictable `settings.json.tmp` filename shared by concurrent writers.

Project JSON, recent-project history, and diagnostics export use the same unique atomic text-persistence primitive. Publication manuscript transactions remain a separate, stronger multi-file transaction system.

## Settings loading and forward/backward tolerance

`AppSettings.load()`:

- returns default settings if the file does not exist;
- returns safe defaults if the settings file cannot be decoded/read as valid JSON;
- requires the top-level JSON value to be an object;
- keeps only keys known by the current `AppSettings` dataclass;
- ignores unknown keys;
- rejects stored values whose primitive type does not match the setting's default type;
- clamps `worker_count` to `1–64` and `text_scale_percent` to `80–200`;
- resets invalid theme/logging/PDF-optimization/DOCX-fidelity/profile values to their safe defaults; and
- supplies dataclass defaults for missing or rejected keys.

Application settings and recent history are recoverable convenience metadata, so a damaged local preference file must not make the GUI unusable. Saved merge-project files are different: their loader remains strict and surfaces malformed project JSON rather than guessing publication-critical configuration.

## App settings versus project settings

Do not confuse the two layers.

### App settings

User/default desktop preferences such as theme, logging, history, text scale, and defaults for new workflows.

### Project settings

Saved publication-specific behavior such as expected parts, overwrite, filename template, PDF settings, and DOCX settings.

The project should remain reproducible even when another machine has different desktop preferences, so always inspect the saved project and dry-run evidence before publication.

## Privacy considerations

A settings file can reveal:

- default output/temp paths;
- preferred profile/modes;
- usage preferences.

It should not contain manuscript bodies or encrypted-PDF passwords.

On a shared system, store settings under the appropriate user account/profile and review recent-project behavior.

## Safe settings-change procedure

After changing publication-affecting defaults:

1. save settings;
2. reopen/create the intended project;
3. verify project-specific settings were actually updated if desired;
4. run project dry-run;
5. inspect expected outputs, fidelity mode, checksums, validation, and storage;
6. run a representative test publication before a high-value release.
